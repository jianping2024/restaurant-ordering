# 同行组：解散回列表 + 加人同一套餐

## 本次修改

1. 解散 / 组消失后主区停在同行组列表（不跳楼面）
2. 加人勾选锁定同一套餐（不同类灰显）；服务端 `buffet_mismatch`

## 核心业务规则

- 组没了 → 同行组列表；组还在 → 留在该组详情
- 同一同行组只能一种套餐（与并台同口径：有/无套餐也算不同）
- 勾选后不同套餐灰显不可勾；服务端再拦

## 详细测试场景

### 场景 1：解散后回列表

- **前置**：楼面看板；已有空同行组；在组详情
- **操作**：点解散 → 确认
- **预期**：顶栏「同行组」仍选中；主区是列表（可创建）；不是楼面桌卡
- **结果**：【已验证】UI（localhost:3002）

### 场景 2：同套餐可加入

- **前置**：空同行组；两桌用餐中且同一套餐
- **操作**：API `add_tables` 加入两桌
- **预期**：200，成员写入
- **结果**：【已验证】API

### 场景 3：不同套餐不可同组

- **前置**：干净数据
- **操作**：`resolvePartyBuffetLock(['b1','b2'])` / `['b1', null]`
- **预期**：`conflict`；UI 灰显；服务端 409 `buffet_mismatch`
- **结果**：【已验证】单测；【未验证】本店仅一种套餐，未实点两种套餐灰显 / API 409

### 场景 4：回归 — 创建后进详情

- **前置**：同行组列表
- **操作**：点创建
- **预期**：进入新组详情（可加桌/解散）
- **结果**：【已验证】UI

### 场景 5：详情返回控件

- **前置**：组详情
- **操作**：看左上返回；点击
- **预期**：`← 同行组`（与桌台详情回看板同款 soft+action，约 52px）；点后回列表
- **结果**：【已验证】UI（高度 52；回列表）

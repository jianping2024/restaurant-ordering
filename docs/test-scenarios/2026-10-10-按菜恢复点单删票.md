# 本次改动业务场景测试报告：按菜分单「恢复点单」= 删票

日期：2026-10-10 · 分支：`fix/by-item-release-no-marker` · 环境：本地 :3002（worktree，`.next-uat`）+ 本地 Docker Supabase · 测试店：白云 `restaurant-mohnrib5`

## 1. 本次修改

- **问题**：按菜分单，同一个人收过一次款后再次呼叫结账，员工在结账页对新票点「恢复点单」，只有按钮消失，这个人的票（人、菜、金额）仍留在页面上，分单也卡在「结账中」不放开。
- **改动**：
  - 迁移 `20261010190000_by_item_unlock_deletes_ticket.sql`：`individual_checkout_apply(unlock)` 改为删票。同一事务内删除该票的人员行、结果行和呼叫行，把排在后面的票的 `session_collected_payments.person_index` 前移；解锁后若已没有「已呼叫且未付」的票，清掉 `staff_checkout_requested_at`。
  - `individual-checkout-server.ts`：解锁不再上传分单行（以服务端存量为准）。
  - 注释与文档同步：`ai-schema.md`、`guest-individual-checkout.zh.md`、`AGENTS.md`。
- **角色 / 页面**：员工结账页（份额区「恢复点单」）、结账队列、楼面「呼叫结账」入口；客人手机读取同一分单。
- **不在范围**：整桌、均摊；收款改按票编号记账（另做）；历史遗留 `state='unlocked'` 票（保持原样，只读兼容）。

## 2. 核心业务规则（不变量）

1. 恢复点单只删**这一张未付票**；已付票、正在收款的票不能删。【已实现】
2. 删票后，其他票的收款不错位（收款按结果下标记账）。【本次新增】
3. 删票后菜回到剩余菜品，可重新分。【本次新增】
4. 已没有「已呼叫且未付」的票时，分单回到 `confirmed`，这桌离开结账队列。【本次新增】
5. 还有别人在呼叫时，分单保持 `requested`。【已实现】
6. 同一张票被同时恢复两次，只删一次。【已实现，靠修订号 + 行锁】

## 3. 详细测试场景

### 场景 1：同一人收款后再呼叫，员工恢复点单（原问题）
- **前置**：VIP888 开台（自助 1 人 + 冰水×2、中水×2、Imperial×1）。客人手机 Jj 呼叫第 1 张，员工收款；Jj 再呼叫第 2 张，员工收款（菜未分完，系统贴接管标签）；Jj 再呼叫第 3 张（002 冰水）。
- **操作**：员工打开结账页 VIP888，份额区点「恢复点单」。
- **预期**：提示「已恢复点单」；VIP888 离开队列；第 3 张票人、菜、金额全部消失；已付的两张和收款记录不变；分单 `confirmed`、标签清空；桌子仍营业。
- **结果**：【已验证】pass。库内：`confirmed | 标签 f | Jj:true,Jj:true`，收款 2 条（下标 0、1）不变，会话 `open`。

### 场景 2：删中间一张票，后面已付票的收款不错位
- **前置**（数据库事务内构造，回滚）：A 已付（下标 0）、B 未付已呼叫（1）、C 已付（2）、D 未付已呼叫（3），收款 A→0、C→2，标签已贴。
- **操作**：解锁 B；再解锁 D；再尝试解锁已付的 A。
- **预期**：B 删除后 C 的收款下标 2→1；D 还在呼叫时分单保持 `requested`、标签保留；D 删除后分单 `confirmed`、标签清空；解锁 A 被拒（`ticket_paid`）。
- **结果**：【已验证】pass（T1–T10 全部符合）。

### 场景 3：恢复点单后，员工在楼面点「呼叫结账」
- **前置**：场景 1 之后（只剩两张已付票，菜未分完）。
- **操作**：员工楼面点「呼叫结账」（`ensure-entry`），跳转结账页。
- **预期**：这桌进入队列，详情能打开；被删票的 002 冰水回到剩余菜品（可分 1）。
- **结果**：【已验证】pass。

### 场景 4：两名员工同时恢复点单同一张票
- **操作**：两个请求同时调用 `unlock-ticket`。
- **预期**：一个成功，一个返回票不存在；只删一次，收款不变。
- **结果**：【已验证】pass（一个 200，一个 404 `ticket_not_found`；结果 2 行、收款 2 条）。

### 场景 5：已收一部分钱的票不能恢复点单
- **操作**：Jj 呼叫新票（€1.85），员工先收 €1.00，再点恢复点单。
- **预期**：拒绝（`ticket_collecting`），票和收款都不变。
- **结果**：【已验证】pass（409 `ticket_collecting`）。

### 场景 6：整桌回归
- **操作**：VIP999 开台 → 员工呼叫结账（整桌）→ 整桌恢复点单。
- **预期**：呼叫后桌子 `billing`、分单 `requested`；恢复后桌子 `open`、分单 `cancelled`。
- **结果**：【已验证】pass。

### 覆盖维度说明
- 本地与服务端：解锁以服务端存量为准，客户端不再上传分单行。员工页刷新后按服务端重建草稿，场景 1 页面即时消失。【已验证】
- 客人手机：页面开着时本机选择保留在内存；刷新或换手机后不再从服务端恢复。【未验证】（只读代码，没在手机页面实测）
- 均摊：不走解锁函数（`split_mode_locked`），代码未改。【未验证】
- 转台、并台：只读取分单状态，逻辑未改。【未验证】
- 历史遗留 `state='unlocked'` 票：保持原样，只读兼容。【未验证】

# 本次改动业务场景测试报告：收款调整开台人数复用开台锁价

日期：2026-10-23  
分支：`fix/checkout-reuse-locked-buffet-prices`

## 1. 本次修改

- **内容**：自助餐成人/儿童单价在开台写入 `buffet_base` 行后锁死；收款页「调整开台人数」展示与保存优先复用行上单价，不再因「已叫结」清空价表，也不对已锁套餐按当前时刻重匹配时段。
- **文件**：`buffet-order.ts`（唯一读锁/合并）、`buffet-waiter-pipeline.ts`、`waiter-table-detail-load.ts`、`CheckoutRequestDetailHost.tsx`、`buffet-order.test.ts`、`docs/agent-sole-index.zh.md`
- **角色 / 页面**：收银/店长 · 收款详情 · 调整开台人数弹窗；服务员写人数保存路径

## 2. 核心业务规则

1. 有未作废 `buffet_base` 且行上成人/儿童单价齐全 → 预览与改人数写单必须用该单价（【本次新增】明确为唯一写法）。
2. 尚无锁价行（从未写过该套餐）→ 才调用 `resolve_buffet_prices`（【已实现】保留）。
3. 「当前时段无匹配价格」仅当无锁价且现查也无规则时出现（【本次新增】纠正叫结空表误报）。
4. 已锁套餐改人数不得因时刻变化改单价（【本次新增】）。

## 3. 详细测试场景

### 场景 1：开台 0 人锁价后，收款调整人数应显示开台单价

- **前置状态**：启用自助餐的店；某桌开台并写入自助餐行（可为 0 成人 0 儿童），行上已有成人/儿童单价；客人已叫结，收款详情弹出「开台人数为 0」。
- **操作过程**：选「调整人数」→ 看 Rodizio/套餐下单价文案 → 改为成人 ≥1 → 确认。
- **预期结果**：弹窗显示开台时单价（非红字「无匹配价格」）；确认后账单人头与金额 = 人数 × 锁价。
- **数据验证**：订单行 `adult_unit_price`/`child_unit_price` 与改前一致；仅人数与行金额变。
- **异常恢复**：取消弹窗可回到软确认；不重复写价。
- **标签**：【已验证】见下方实测

### 场景 2：已锁价套餐在晚间改人数，单价不变

- **前置状态**：午市开台锁价；桌仍在餐中或已叫结；系统当前时刻已落入另一时段且该时段规则价不同。
- **操作过程**：收款或写人数接口把成人从 1 改为 2。
- **预期结果**：新行仍用开台锁价，不用晚市现查价。
- **数据验证**：保存前后 `adult_unit_price` 相同。
- **异常恢复**：无。
- **标签**：【已验证】单元（merge 优先锁价）+ API 改人数后读行；【未验证】真跨时段墙钟（本机用锁价覆盖 live 模拟）

### 场景 3：从未写过自助餐行，收款首次登记人数

- **前置状态**：店有启用套餐；桌已开台但无 `buffet_base`；已叫结。
- **操作过程**：调整人数并确认。
- **预期结果**：无锁价 → 现查规则；有规则则显示现价并写入；无规则则红字且确认失败。
- **数据验证**：新行单价 = 当时 `resolve_buffet_prices`。
- **标签**：【未验证】本机 UAT 以「已有锁价行」为主路径；规则与现查路径未单独拆桌

### 场景 4：楼面未叫结改人数仍可用（回归）

- **前置状态**：未叫结占用桌，已有自助餐行。
- **操作过程**：楼面加减人数自动保存。
- **预期结果**：人数更新成功；已锁套餐单价不变。
- **标签**：【已验证】API `intent=save` 改人数

### 场景 5：权限与跨端

- **前置状态**：收款端改人数；楼面同桌。
- **操作过程**：收款确认人数后刷新楼面/账单。
- **预期结果**：人数与金额一致，无双价。
- **标签**：【已验证】API 读订单行；【未验证】双浏览器 Realtime 同屏（非本改动核心）

## 5. 风险与待确认

- 历史行若缺 `adult_unit_price`/`child_unit_price`：会走现查；旧数据需留意。
- `resolveOpenTableBuffetPrices` 仍只拉默认套餐 live 价；多套餐无锁价时非默认套餐仍依赖客户端补拉或锁价图——本改以锁价复用为主。

## 2. 核心业务规则（不变量）

1. 【本次新增】送厨成功收口 **不清** 各机 `cart`；免费/收费草稿均保留。  
2. 【已实现】清空购物车的唯一产品路径仍是本机「下单」成功后的 `clearSubmitCart`（及用户手动清空）。  
3. 【已实现】送厨成功边沿判定仍 sole `isKitchenSendSuccessStatusTransition`；整桌仍关浮层 + toast。  
4. 【已实现】冷却期内再加免费菜仍拦；未下单草稿不会因别人送厨进入厨房。  
5. 【设计建议·未改】多机草稿互不可见；抢额度仍以服务端写入为准。

## 3. 详细测试场景

### 场景 1：他机仅有免费草稿 — 一机送厨后草稿仍在

- **前置状态：** 同桌两台客人菜单（不同浏览器上下文）；桌已开台且寿司轮次可用。手机 A 已有至少 1 道免费菜进本轮篮；手机 B 只把免费菜放进购物车，**不点「下单」**。  
- **操作过程：** A 打开核单 → 送厨本轮 → 确认 → 等到 status 进入冷却（或倒计时到点 finalize）。  
- **预期结果：** B 弹出/看到「本轮已送厨」类提示；核单等浮层可关；**购物车里 B 的免费草稿份数仍在**（抽屉可能被关掉，打开后仍有菜）。  
- **数据验证：** B 本机 `cart` 非空；round 已 `cooldown`；B 的草稿未出现在本轮已送厨订单行（因从未下单）。  
- **异常恢复：** B 刷新后草稿可能丢（本机内存态，非本次范围）；冷却中点免费加份应提示冷却中。

### 场景 2：本机下单成功仍清空购物车（回归）

- **前置状态：** 单机；购物车有免费菜草稿。  
- **操作过程：** 点购物车「下单/加入本轮」成功。  
- **预期结果：** 购物车清空；菜出现在本轮核单/托盘角标。  
- **数据验证：** `clearSubmitCart` 路径；round lines 含本机行。  
- **异常恢复：** 下单失败时购物车应保留（既有行为）。

### 场景 3：送厨成功仍关浮层 + toast（回归）

- **前置状态：** A 开着核单；B 可开可不开购物车抽屉。  
- **操作过程：** 送厨成功进入冷却。  
- **预期结果：** A/B 核单/确认类浮层关闭；有「本轮已送厨」反馈；**不**要求清空 B 的车。  
- **数据验证：** UI 回到点餐壳；底栏可呈已送厨/冷却引导。  
- **异常恢复：** `finalize_failed` 不关核单（既有，本次未改）。

### 场景 4：混合车 — 收费草稿在送厨后仍在（回归加强）

- **前置状态：** B 购物车同时有免费草稿 + 收费菜草稿（未提交）。  
- **操作过程：** A 送厨成功。  
- **预期结果：** B 车内免费与收费草稿都还在（修前免费会被滤掉、收费保留；修后两者都保留）。  
- **数据验证：** 打开购物车可见两类行。  
- **异常恢复：** 冷却期收费菜仍可单独下单（既有）。

### 场景 5：经典堂食不受影响（回归）

- **前置状态：** 非寿司店客人菜单（若本轮 UAT 时间紧可标未验证）。  
- **操作过程：** 正常加车下单。  
- **预期结果：** 无 `dismissToMenuAfterKitchenSend`；行为与改前一致。  
- **数据验证：** 无 sushi round cooldown 清车路径。  
- **异常恢复：** 不适用。

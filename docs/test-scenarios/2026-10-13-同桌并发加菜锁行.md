- 新迁移：`supabase/migrations/20261013120000_append_order_items_row_lock.sql`
- `writeAppendBatch` 只调该 RPC，删除应用层无锁「读 items → 拼 → 整份 update」

- 角色/页面：顾客 `orders/append`；服务员代点/寿司 finalize/菜品历史补单共用 `writeAppendBatch`

## 核心业务规则

1. 同餐次仍合并进最新一张订单（产品规则不变）。
2. 多人几乎同时加菜：每次成功加菜都必须留在订单 `items` 里，不能互相盖掉。
3. 同一 `client_request_id` 仍只写一次（原有幂等不变）。
4. 接口说成功 → 库里必须有对应批次（本轮 note 可对账）。

## 详细测试场景

### 场景 1：同桌 8 人几乎同时加菜

- **前置状态**：Washoku Sushi A-03 开台；`MESA_UAT_BASE=http://localhost:3002`
- **操作过程**：8 个不同 `client_request_id` 同一瞬间各加 1 份咖啡
- **预期结果**：HTTP 成功 8；带 race8 note 前缀的行 = 8
- **数据验证**：staff 桌详情 `items` 对账
- **结果**：【已验证】pass（http_ok=8, persisted=8, lost=0, ~213ms）

### 场景 2：同桌 20 人几乎同时加菜

- **操作**：同场景 1，N=20
- **预期**：成功数 = 落库行数 = 20
- **结果**：【已验证】pass（http_ok=20, persisted=20, lost=0, ~439ms）

### 场景 3：两请求错开加菜（日常节奏）

- **操作**：先 append 成功，再 append 另一 note
- **预期**：两行都在
- **结果**：【已验证】pass（persisted=2）

### 场景 4：同号重试不双写

- **操作**：同一 `client_request_id` 连续两次 append
- **预期**：第二次 `idempotent_replay`；菜不加倍
- **结果**：【已验证】pass（replay=true, persisted=1）

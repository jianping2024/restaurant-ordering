# 2026-10-20 · 菜品供应时段（本次改动业务场景测试报告）

## 本次修改

- 菜品新增「供应时段」：编辑菜品时单选「全天」或已有时段（复用自助餐的「时段」设置）。默认全天，老菜品都是全天。
- 顾客菜单（经典、寿司、员工代点共用同一视图）只显示本桌时段的菜和全天菜。整类都属于其他时段的分类、其他时段的推荐菜一起隐藏。
- **本桌时段的判定**：按开台时间 `opened_at`（里斯本时间 + 星期）取**最近**的时段，开台后到关台不变；还没开台只浏览时按当前时间算。时段的结束时间不让菜品下线。
- 服务端写入门：`orders/append`（经典追加、员工代点、寿司收费菜）、寿司轮次送厨、寿司轮次加份都会拒绝不属于本桌时段的菜，错误码 `menu_item_off_time_slot`，顾客端提示「该菜品不在本时段供应，请刷新菜单后重试。」
- 数据：`menu_items.time_slot_id`，用复合外键 `(restaurant_id, time_slot_id)` 保证只能选本店时段；删除时段时这些菜自动变回全天。时段增删改后让顾客菜单缓存失效。

涉及角色：店主（后台菜单、时段设置）、顾客（扫码点餐）、员工（代点）。

## 核心业务规则（不变量）

1. 「全天」菜任何时候都显示、都能下单。
2. 绑了时段的菜，只在**本桌时段**里显示和下单；本桌时段由开台时间决定，开台后到关台不变。
3. 本桌时段 = 离开台时间最近的时段：超时营业（午餐 15:00 结束，客人吃到 16:30）不会下线午餐菜；提前开餐（晚餐 19:00 开始，18:30 开台）直接用晚餐菜单。午餐 12–15、晚餐 19–23 时，切换点是 17:00。
4. 页面上的菜单可能过期，服务端是最终裁决：不属于本桌时段的菜一律拒绝，同一请求中的其他菜也不写入（整单拒绝、不部分写入）。
5. 菜品只能绑定本店的时段（跨店 id 被外键拒绝）。

## 详细测试场景

### 场景 1：店主给菜品设置「午餐」并在列表看到

- **前置**：白云 `restaurant-mohnrib5` 有时段 午餐 12:00–15:00、晚餐 19:00–23:00；店主 baiyun 登录后台；菜品 201 茉莉花茶为全天。
- **操作**：菜单管理 → 菜品 → 分类「茶」→ 201 茉莉花茶「编辑」→「供应时段」看到 全天 / 午餐 / 晚餐 三个 chip，默认选中全天 → 点「午餐」→ 保存修改。
- **预期**：保存成功；列表 meta 显示「供应时段: 午餐」。
- **数据验证**：`menu_items.time_slot_id` = 午餐 id；`menu_catalog_version` 递增。
- **结果**：【已验证】pass（chip 选中状态 aria-checked 正确；库里是「午餐」；列表截图可见「供应时段: 午餐」）。

## 风险与待确认

1. **时段切换点是自动算出的中点**（午餐 12–15、晚餐 19–23 → 17:00）。如果两个时段之间间隔很短（比如 15:00 结束、15:30 开始），切换点会变成 15:15，超时营业超过 15 分钟的桌也不受影响（按开台时间固定），但 15:15 之后新开的桌就是下一时段。
2. 开台时间就是判定依据：员工如果提前很早开台（比如 16:50 为 19:00 的预订开台），这桌会按午餐算。需要的话以后再加「员工改本桌时段」。
3. 时段表与自助餐价格共用：删除时段会同时影响自助餐价格规则，这是原有行为；菜品会自动变回全天。
4. 时段的「适用星期」也生效：某天没有任何时段运行时，绑了时段的菜当天都不显示，只显示全天菜。
5. 本地库已用 psql 应用迁移（幂等）；推送云端前按 runbook 走 `db push`。

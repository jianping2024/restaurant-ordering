## 1. 改动摘要

- 判定函数 `narrowMenuItemsToTableBuffet`（`apps/web/src/lib/instore-takeaway.ts`）：输入是已经过渠道和时段过滤的菜。
  - 如果有 ≥1 道已上架菜配了本桌套餐价（0 元也算），只保留配了价的菜；否则全部显示。
  - 外卖桌、没有套餐的桌不收窄。
  - 「是否配价」的判断和取价 `menuItemUnitPriceForChannel` 共用私有函数 `menuItemBuffetConfiguredPrice`。
- 挂载点 `resolveCustomerMenuCatalogView` 新增两个入参：
  - `tableBuffet`：`{ buffetId, buffetPrices, staffAssisted }`，或 `null`。在渠道和时段过滤之后套用。
  - `dietaryPrefs`：寿司页的饮食过滤移到收窄之后，避免「只看素食」把收窄翻成全显。
  - 新增返回值 `buffetHiddenItemIds`。
- 购物车 `repriceCartLines(cart, items, hiddenItemIds)`：被收窄藏掉的菜会从购物车移除。
- 三个调用方：
  - 经典页：`staffAssisted: !!staffAssisted`。
  - 寿司页：`staffAssisted: false`。寿司页从不会给员工打开（`shouldRenderSushiRoundMenuPage`）。
  - 店面预览：`tableBuffet: null`。
- 后台 `MenuItemBuffetPricesField` 加了三语提示 `buffetPricesGuestMenuHint`。
- 删除死代码：
  - 删掉 `buffet-switch-reprice.ts` 和对应 test。
  - 新增 migration `20261119120000_drop_switch_table_buffet.sql`，保留 `order_item_is_buffet_priced`。
  - 同步更新 `docs/ai-schema.md` 和 `docs/agent-sole-index.zh.md`。
- 营业中改套餐价会不会通知客人页：已核实会。保存菜品价格（`dashboard-menu-server.ts` 新建和更新两处）都会调用 `invalidateCustomerMenuCatalog`。实测 lucky-tea 的 `menu_catalog_version` 改两道菜价后从 627 变成 629。所以这部分没有补代码。

```python
html = urllib.request.urlopen(url).read().decode()
visible = re.sub(r'<script[\s\S]*?</script>', '', html)
bad = [t for t in texts if (t in visible) != (mode == 'present')]
sys.exit(1 if bad else 0)
```

## 4. 反证（证明测试本身有效）

- **同一页面前后对比**：C1→C2、C4→C5、C6 下架→上架、S1→S2→S4，都是在同一个标签页里、不刷新，看到 Fanta、REFRIGERANTE、BEBIDAS、Água Frio 出现又消失。SSR 机器证据里，同一个 URL 在不同数据状态下分别断言了 `present` 和 `absent`，都是 exit=0。所以检查脚本确实能分辨这两种状态。
- **单测在改动前会失败**：把新的 `menu-recommended.test.ts` 拷到 `git archive HEAD`（改动前的代码）里运行，结果是 `# pass 15 / # fail 9`：
  - `narrowMenuItemsToTableBuffet` 的 4 条：`is not a function`。
  - view 收窄的 4 条：没有收窄，或者 `buffetHiddenItemIds` 为 undefined。
  - 购物车的 1 条：Fanta 没有被移除。
  - 原有的 15 条照常通过。

  改动后同一批测试是 61/61 通过（另外 4 个相关测试文件也一起跑了）。

## 5. 失败与修复记录

1. **寿司第一次浏览器跑，S4 证据作废。** 子代理按屏幕坐标点击想关闭购物车，结果点中了「Enviar pedido」，把 Água Frio 下单了（库里 A-19 出现 Água Frio 1.85 一行）。这样就分不清购物车是被收窄清空的，还是被提交清空的。处理：换一个子代理重跑 S2–S4，要求只用 ref 点击、用 Escape 关闭、记录「Pedidos feitos」计数。重跑时计数一直是 (1)，库里 Água Frio 行数仍为 1，证据才算成立。误下的单随测试桌一起以 `test_order` 关台。
2. **寿司第一次跑里，Café 没出现在 innerText 里**（截图里有）。重跑时点 Café 分类，读到「901 Café €3.00」，确认这道菜没丢，是读取时机问题。
3. **把饮食过滤并入 view 是设计阶段发现的问题**：如果先做饮食过滤再收窄，「只看素食」会让配价菜被全部滤掉，收窄判定就会翻成全显。现在收窄放在饮食过滤之前，由单测覆盖。
4. **代码审查（Opus 子代理）**：没有发现正确性 bug。处理情况：
   - `ai-schema.md` 的文案原来是「any served dish」，已改为「any available served dish」。
   - `next dev` 改写了 `apps/web/tsconfig.json`，已还原，不提交。
   - 风险（按方案可接受，未改）：寿司「本轮核单」可以给自己已有的轮次行 +1。如果那一行恰好是后来才被收窄藏掉的菜，客人仍能加。方案规定服务端不门禁，所以没处理。
5. **记录证据时 zsh 的变量没有按词拆开**，第一批 `uat-evidence` 没有执行。改成 shell 函数重跑，所有证据行都是 exit=0。

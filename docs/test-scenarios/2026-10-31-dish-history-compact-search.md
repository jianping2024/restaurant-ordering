# 本次改动业务场景测试报告：当日菜品筛选条对齐操作记录

日期：2026-10-31  
分支：`fix/dish-history-compact-search`

## 1. 本次修改

- **内容**：当日菜品页顶部筛选改成与操作记录相同的横排工具条：无「桌号 / 菜名」字段标题；菜名或编号用同一套紧凑搜索框样式；桌号仍用原有多选控件。
- **文件**：`DishHistoryManager.tsx`、`OperationLogsManager.tsx`（共用紧凑搜索 class）、`form-control-text.ts`、`messages.ts`、`docs/agent-sole-index.zh.md`
- **角色 / 页面**：店主或有「当日菜品」权限的员工 → `/dashboard/dish-history`；顺带确认操作记录页搜索框未坏。
- **行为不变**：仍只查里斯本当天菜品；打字/改桌号仍防抖自动查；补单、分页不变。

## 2. 核心业务规则

1. 当日菜品列表仍是里斯本当天 + 分页；筛选条件仍是菜名/编号 `q` 与桌号 `table_ids`。【已实现】
2. 后台列表紧凑搜索框样式只有一份：`DASHBOARD_COMPACT_SEARCH_CLASS`（当日菜品与操作记录共用）。【本次新增】
3. 桌号筛选仍只有 `DashboardTableMultiSelect`，不另做下拉。【已实现】
4. 无单独「搜索」按钮；改条件即查。【已实现】

## 3. 详细测试场景

### 场景 1：打开当日菜品，筛选条形态

- **前置状态**：店主已登录（`luckytea@gmail.com`）；浏览器打开当日菜品页。
- **操作过程**：进入 `/dashboard/dish-history`，看顶部筛选区。
- **预期结果**：桌号多选与菜名搜索在同一横排；上方无「桌号」「菜名或编号」标题；搜索框为小尺寸（约 11rem），与操作记录搜索框同类。
- **数据验证**：不改列表接口字段。
- **异常恢复**：不适用。

### 场景 2：按菜名搜索

- **前置状态**：当日有菜品记录（或空列表亦可验证空态文案）。
- **操作过程**：在搜索框输入菜名或编号片段，等待防抖后列表刷新。
- **预期结果**：列表只显示匹配行；清空搜索后恢复更宽结果。
- **数据验证**：请求带 `q=`；页码回到合理范围（hook 行为）。
- **异常恢复**：刷新页面后筛选草稿按组件初始为空。

### 场景 3：按桌号筛选并与搜索组合

- **前置状态**：店内有多张桌。
- **操作过程**：先选一张桌 → 再输入菜名；再取消桌号。
- **预期结果**：仅该桌匹配菜品；组合条件收窄；取消桌号后只按菜名。
- **数据验证**：请求带 `table_ids` 与可选 `q`。
- **异常恢复**：不适用。

### 场景 4：操作记录搜索框回归

- **前置状态**：有操作记录查看权限。
- **操作过程**：打开 `/dashboard/operation-logs`，看搜索框并可输入。
- **预期结果**：外观与改前一致（仍为紧凑搜索）；输入后仍可筛列表。
- **数据验证**：不新增平行 class。
- **异常恢复**：不适用。

### 场景 5：补单与分页未破坏

- **前置状态**：列表有可补单行（会话仍开台）或至少分页控件可见。
- **操作过程**：若有开台行则点补单弹窗取消；切换每页条数或翻页（有数据时）。
- **预期结果**：补单弹窗仍可用；分页控件仍工作。筛选样式改动不挡住这些操作。
- **数据验证**：无接口契约变更。
- **异常恢复**：关闭弹窗后列表仍在。

### 场景 6（顺序）：先搜后选桌 vs 先选桌后搜

- **前置状态**：有多桌当日菜品。
- **操作过程**：顺序 A：先输入菜名再选桌；顺序 B：先选桌再输入同一菜名。
- **预期结果**：两种顺序最终列表一致（同一 `q` + `table_ids`）。
- **数据验证**：最终 query 相同。
- **异常恢复**：不适用。

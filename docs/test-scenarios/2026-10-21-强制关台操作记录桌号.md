# 本次改动业务场景测试报告：强制关台操作记录桌号

日期：2026-10-21

## 1. 本次修改

- **内容：** 强制关台写入操作记录时，在 `after_data` 带上桌号（`tableName`），与开台/关台结账一致；操作记录「桌位」列与按桌号搜索仍只读这一字段。
- **文件：**
  - `apps/web/src/lib/audit/builders/unpaid-table-closed.ts`
  - `apps/web/src/lib/audit/builders/unpaid-table-closed.test.ts`（新增）
  - `apps/web/src/lib/operation-logs/operation-logs.test.ts`（补断言）
- **角色 / 页面：** 有强制关台权限的员工或店主；Dashboard「操作记录」。
- **流程：** 未付强制关台 → 写 `UNPAID_TABLE_CLOSED` → 列表「桌位」显示桌号 → 按桌号搜索可命中。

## 2. 核心业务规则

1. 操作记录「桌位」与按桌号搜索：**只认** `operation_logs.after_data.tableName`（【已实现】）。
2. 强制关台审计写入时，`after_data` **必须**含 `tableName`（与顶层 `tableName` 给异常台账列并存；展示不另开读法）（【本次新增】）。
3. 旧记录若 `after_data` 无桌号，列表仍为 `—`；本次不做历史回填（【设计建议】未做）。
4. 异常操作台账的 `table_name` 列行为不变（【已实现】）。

## 3. 详细测试场景

### 场景 1：强制关台后操作记录显示桌号

- **前置状态：** 店主登录 Washoku（`lucky-tea-mulcs62n`）；某桌有未付餐次（如 A-05）。
- **操作过程：** 店主对该桌强制关台（确认 + 原因 `left_unpaid`）；打开操作记录，筛「强制关台」或查最新一条。
- **预期结果：** 「操作」= 强制关台；「桌位」= 该桌 `display_name`（非 `—`）；「详情」仍有未付金额文案。
- **数据验证：** 最新 `operation_logs` 行 `action_type=UNPAID_TABLE_CLOSED`，`after_data.tableName` = 桌名；同批 `abnormal_operations.table_name` 仍有桌名。
- **异常恢复：** 刷新列表后桌号仍在。

### 场景 2：按桌号搜索能命中强制关台

- **前置状态：** 场景 1 已写入带桌号的强制关台记录。
- **操作过程：** 操作记录搜索框输入该桌号（如 `A-05`），可叠加动作筛「强制关台」。
- **预期结果：** 出现该强制关台行。
- **数据验证：** 列表 API `q` 命中 `after_data->>tableName`。
- **异常恢复：** 清空搜索后仍可按动作筛到。

### 场景 3：开台等其它操作桌号不受影响（回归）

- **前置状态：** 同店有近期开台或关台结账记录。
- **操作过程：** 操作记录查看非强制关台行（如开台）。
- **预期结果：** 「桌位」仍显示桌号；强制关台改动未改读侧。
- **数据验证：** `operationLogTableLabel` 仍只读 `after_data.tableName`。
- **异常恢复：** 不适用。

### 场景 4：历史强制关台无桌号行（兼容）

- **前置状态：** 改前已写入的 `UNPAID_TABLE_CLOSED`（`after_data` 无 `tableName`）。
- **操作过程：** 列表筛强制关台看旧行。
- **预期结果：** 旧行「桌位」仍为 `—`（未回填）。
- **数据验证：** 旧行 `after_data` 仍无 `tableName`。
- **异常恢复：** 不适用。

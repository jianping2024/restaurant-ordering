## 2. 核心业务规则

1. 谁付过钱、谁的菜不能改：有 id 用 id  
2. 一行同时有 id 与下标且对不上 → **只认 id**，忽略下标  
3. 旧台账没有 id → 仍用下标（兼容历史）  
4. 芯片 ✓ / 某人已收（原已 id 优先）与锁菜口径必须一致

## 3. 详细测试场景

### 场景 1：id 与下标冲突 — 只锁已付票（Farvoo 桌 90 复现）

- **前置**：`result` = Pedro(已付,id=A) · Y(未付,id=B)；台账 `party_id=A`、`person_index=1`（指向 Y）、金额=Pedro 已收  
- **操作**：`allocationLockedTicketKeys`；`applyCollectedObligationFloors`  
- **预期**：锁 A 不锁 B；Y 义务不被 Pedro 已收抬高  
- **标签**：【本次新增】【已验证】（单测 `party_id wins over stale person_index` + floor 用例）

### 场景 2：旧台账无 party_id — 仍按下标锁

- **前置**：台账 `party_id=null`、`person_index=1`  
- **操作**：`allocationLockedTicketKeys` / `ledgerPaymentTicketKey`  
- **预期**：锁下标对应票，不误锁其他票  
- **标签**：【已实现】【已验证】（单测）

### 场景 3：正常按菜 — 收一人后另一人仍为未付

- **前置**：本地 A-04 开台 Rodizio×2A；按菜 Pedro / Y 各 1A  
- **操作**：`POST …/checkout/request` → `POST …/confirm-payment` 收 Pedro €17.90（`party_id`）→ 故意把台账 `person_index` 改成 1（制造冲突）→ 打开结账页 A-04  
- **预期**：Pedro `result.paid=true`；台账仍挂 Pedro 的 id；锁菜集合含 Pedro 不含 Y（单测同构）；页上有「已有收款」提示、Pedro 姓名框禁用  
- **数据验证**：库内 payment `party_id=Pedro`、`person_index=1`；split result Pedro paid / Y unpaid  
- **标签**：【本次新增】【已验证】（API + SQL + 浏览器见锁提示/Pedro 禁用）；份额区 Rodizio 金额显示 €0.00 为本夹具 hydrate 显示问题，Y 份额按钮点击【未验证】（无可靠可点 chip）

### 场景 4：回归 — 结算认人仍 id 优先

- **前置**：同场景 3  
- **操作**：确认收款响应含 `collection.party_id`；页面折扣因有收款锁定  
- **预期**：收款按 id 落库；与锁菜新口径一致  
- **标签**：【已实现】【已验证】（confirm-payment 200 + `party_id`）

### 场景 5：回归 — 聚焦单测全绿

- **操作**：`checkout-split-continuation` / `checkout-by-item-collect` / `checkout-session-payments`

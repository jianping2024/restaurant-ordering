## 2. 核心业务规则

1. 【本次新增】备餐区卡片身份 = `menuItemId` + `lineNoteKey`（trim；空串 = 无备注）；sole `prepTrayCardKey`。
2. 【本次新增】同菜同备注可叠；有备注与无备注、或备注文本不同 → 拆成不同卡，份数各自累计。
3. 【已实现】备餐提交仍按订单行键；不改左侧按桌/按菜行粒度。
4. 【已实现】卡上有备注时琥珀展示 `· {note}`（与工作台行一致可读）。

## 3. 详细测试场景

### 场景 1：同菜有备注 vs 无备注 → 两张卡

- **前置状态**：后厨档口已开；工作台有同一菜两行——一行备注「三分糖」×3，一行无备注 ×1；两行均勾选。
- **操作过程**：厨师在大屏看到备餐区。
- **预期结果**：两张卡；有备注卡「共 3 份」且标题旁有「三分糖」；无备注卡「共 1 份」、无备注文案。
- **数据验证**：`buildPrepTrayCards` 返回 `cards.length === 2`，`note` 分别为 `三分糖` / `''`，`selectedQty` 为 3 / 1。
- **异常恢复**：取消勾选其中一行 → 对应卡消失或仅剩跳过芯片（既有三态）。

### 场景 2：同菜同备注（含 trim）→ 仍叠一张

- **前置状态**：同一菜两行，备注分别为 `三分糖` 与 ` 三分糖 `（前后空格），均勾选。
- **操作过程**：进入备餐区。
- **预期结果**：一张卡，备注显示 `三分糖`，份数合计。
- **数据验证**：`lineNoteKey` trim 后同 key。

### 场景 3：同菜无备注多桌 → 仍叠一张（回归）

- **前置状态**：同菜无备注，桌 A / 桌 B 各一行，均勾选。
- **操作过程**：备餐区。
- **预期结果**：一张卡，两个桌号芯片，份数合计。
- **数据验证**：与改前「按菜叠」行为一致（无备注路径）。

### 场景 4：备餐提交仍按行（回归）

- **前置状态**：场景 1 两张卡均已选。
- **操作过程**：点备餐区「备餐」。
- **预期结果**：两行均 `pending → cooking`；不因拆卡重复或漏备。
- **数据验证**：服务端仍按 `order_id:item_index` 收行。

### 场景 5：左侧按菜一级不因本改动拆备注（回归）

- **前置状态**：同菜有/无备注多行在工作台。
- **操作过程**：切「按菜」视图。
- **预期结果**：一级仍按菜 ID；二级各行自带备注展示（既有）。
- **数据验证**：未改 `aggregateLinesByDish`。

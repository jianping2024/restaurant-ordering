# 菜品删除：有点单记录时提示不能删

日期：2026-11-06  
范围：后台菜单删除菜品 / 分类连菜删除时的占用提示与 Storage 清理顺序

## 核心业务规则

1. 菜品仍被 `table_order_round_lines` 引用时，不能硬删除；接口返回 `menu_item_in_use`（409）。
2. 界面须用业务文案提示「已有点单记录，不能删除；如需对顾客隐藏请先下架」，不得静默失败，不得把数据库外键原文直接当主提示。
3. 只有删除行成功后才清理菜品图/视频 Storage；被占用拒绝删除时，图/视频不得被先删。
4. 从未被轮次行引用的菜，删除仍应成功并从列表消失。

## 详细测试场景

### 场景 1：有点单记录的菜 — 删除被拒并提示

- **前置状态**：店主已登录；菜单里存在至少一道曾出现在寿司轮次行中的菜
- **操作过程**：打开菜单管理 → 点该菜「删除」→ 确认删除
- **预期结果**：弹出「无法删除」；正文说明已有点单记录、不能删除、可先下架；菜仍在列表
- **数据验证**：`menu_items` 行仍在；Storage URL 不变
- **异常恢复**：点「确认」关掉提示后可继续下架或编辑

### 场景 2：从未点过的菜 — 删除成功

- **前置状态**：新建一道测试菜（或确认无 round line 引用）
- **操作过程**：删除并确认
- **预期结果**：菜从列表消失；无占用提示
- **数据验证**：`menu_items` 行已删

### 场景 3：分类「删除分类及全部菜品」含被引用菜

- **前置状态**：分类下有至少一道曾被点过的菜
- **操作过程**：删分类 → 选「删除分类及全部菜品」
- **预期结果**：无法删除提示（分类口径文案）；分类与菜仍在
- **数据验证**：相关 `menu_items` / `menu_categories` 行仍在

### 场景 4：API 错误码

- **前置状态**：同上被引用菜 id
- **操作过程**：`DELETE /api/dashboard/menu/items` body `{ item_id }`
- **预期结果**：HTTP 409，`error: menu_item_in_use`；无外键原文作为唯一用户可见错误码

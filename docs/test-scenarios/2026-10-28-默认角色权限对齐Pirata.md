# 本次改动业务场景测试报告 — 默认角色权限对齐 Pirata

日期：2026-10-28  
分支：`fix/pirata-default-role-permissions`  
UAT 基座：`http://localhost:3003`（feature，`MESA_NEXT_DIST_DIR=.next-uat-pirata-roles`）

## 1. 本次修改

把「厨房 / 服务员 / 收银员 / 前台 / 店主」五套**预制**角色出厂权限，固化成现场 Pirata（`pirata-ms8khtls`）正在用的那一套。

- 产品唯一默认矩阵：`packages/shared` 的 `ROLE_TEMPLATES`（web 再导出）
- 新开云店：`createRestaurantWithOwner` 立刻 `ensureRestaurantPresetRoles`
- 已有云店：migration 把五套预制角色写成同一集合（自定义角色不动；on-prem 不动）
- 「恢复默认」仍读 `ROLE_TEMPLATES`

## 2. 核心业务规则

1. 默认矩阵只有一份：`ROLE_TEMPLATES`；migration 权限数组须与之集合相等（单测锁死）
2. Auth 店主仍是 `*`；「店主」员工预制角色按 Pirata 精简权限
3. `preset_key IS NULL` 的自定义角色不被对齐 migration 改写
4. 开店种子失败则删店+删用户，不留下半成品店

## 3. 详细测试场景

### 场景 1：存量云店预制角色与 Pirata 一致

- **前置状态**：本地 Docker 已应用对齐 migration；云店 `lucky-tea-mulcs62n` 等
- **操作过程**：SQL 对比；owner 登录后 `GET /api/dashboard/roles`
- **预期结果**：服务员无并台；收银有强关台/管桌；店主员工无结账楼面键
- **数据验证**：API 五行与 `ROLE_TEMPLATES` 集合一致
- **标签**：【已验证】

### 场景 2：模板与 migration 同一矩阵

- **操作过程**：`permissions.test.ts` 冻结集 + migration SQL 数组比对
- **预期结果**：全部 deepEqual
- **标签**：【已验证】

### 场景 3：开新云店立刻有五套角色

- **前置状态**：本地 service role
- **操作过程**：`createRestaurantWithOwner` 建临时店 → 查五行 → 再插自定义角色并只更新 preset → 删店与用户
- **预期结果**：五行 = 模板；清理后无残留
- **标签**：【已验证】

### 场景 4：自定义角色不被覆盖

- **操作过程**：在临时店插入 `preset_key=null` 行，再对五套 preset 写回模板

- **标签**：【已验证】

### 场景 5：回归 — 前台/收银/服务员能力推导

- **操作过程**：楼面 / 顶栏 / 桌详情 / access 单测

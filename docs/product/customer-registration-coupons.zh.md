# 客户注册与优惠券（附加功能 · 定稿）

> **状态：定稿 · 未实现**（2026-10-24）  
> **权威：是**（本附加模块的产品口径；与实现冲突时以本文为准，改行为先改本文）  
> **读者**：产品、开发、AI 代理  
> **性质**：可选附加能力。Ops 总闸关闭时，店面行为与现在完全一致——只有扫码点餐 / 现有结账，无注册、无优惠券入口、无券核销。  
> **部署**：云端店与 **on-prem 店均提供**（总闸仍由 Ops 控制；发信见 §4.6）。

相关现状：店主功能开关见 [`../restaurant-features.zh.md`](../restaurant-features.zh.md)；夜间定时任务见 [`../technical/05-deployment.md`](../technical/05-deployment.md)（`/api/cron/nightly-close-sessions`）；结账收款见 [`by-item-collect-payment.zh.md`](./by-item-collect-payment.zh.md)、[`collect-payment-receipt-iva.zh.md`](./collect-payment-receipt-iva.zh.md)。

## 1. 目标

1. 需要本能力的店，由 **Ops 打开总开关** 后，顾客可注册/登录，店员可发券与管理券，结账时可关联使用优惠券。
2. 不需要的店，开关关闭：顾客端与员工端均 **不出现** 本模块任何入口与 API 能力（与「从未开通」等价）。
3. **顾客账号与店内员工账号彻底隔离**——不得共用 Auth 用户、不得用员工会话冒充顾客、顾客不得进入员工后台。

## 2. 功能总开关（Ops）

### 2.1 谁控制（已定）

| 项 | 约定 |
|---|---|
| 控制方 | **Ops**，餐厅详情上的 **独立开关**（**不是**套餐 PlanFeature，**不是**店主 `feature_flags`） |
| 默认 | **关闭** |
| 关时 | 扫码点餐与现有结账不变；无注册/登录/我的优惠券；无券管理页；核销相关 API 一律拒绝 |
| 开时 | 本模块入口与 API 可用；店内可再配置注册送礼、生日送礼、券与折扣是否同用等子配置 |

### 2.2 与现有开关的关系（已定）

| 层 | 谁写 | 本模块是否用 |
|---|---|---|
| Ops 餐厅独立加购开关 | Ops | **是（总闸）** |
| `restaurants.feature_flags` | 仅店主 | **否**（总闸不走这层） |
| Plan / 套餐能力 | Ops | **否**（本版不用 PlanFeature） |

总闸打开后，**店内**再管运营细节（注册送礼、生日送礼、券与员工折扣同用/互斥等）。

### 2.3 关 → 开 / 开 → 关

| 动作 | 行为 |
|---|---|
| 关 → 开 | 顾客端出现注册/登录与「我的优惠券」；店员端出现客户与优惠券管理入口 |
| 开 → 关 | 入口与核销全部停用；**已有客户与券数据保留不删**；未完成收款的已选券不得核销 |

## 3. 账号隔离（硬规则）

| 规则 | 说明 |
|---|---|
| 身份体系分离 | 顾客账号 ≠ `staff` / owner / print_agent；禁止同一登录态跨两边 |
| 作用域 | 顾客账号 **按餐厅**（同一手机号在 A 店注册，不等于自动是 B 店会员） |
| 权限 | 顾客只能：本店资料、本店券、本桌点餐会话内的可选关联；不能访问 dashboard / ops |
| 员工 | 可查看客户档案、代发/作废券；**不得**用顾客登录态进员工端。券在呼叫结账时由顾客选，员工可在结账页调整（见 §8） |

## 4. 客户注册与登录

### 4.1 入口（总闸开启时）

| 表面 | 入口 |
|---|---|
| 顾客手机 · 点餐页 | **注册入口**（常驻、不打断点餐）+ 登录；登录后「我的优惠券」「邀请好友」 |
| 顾客手机 · 呼叫结账 / 结账页 | 已登录 → 可选一张可用券；未登录 → **注册引导**（如"注册即送 €X，本次就能用"），可跳过 |
| 邀请链接 | 打开即进入本店注册页，带邀请人标记（§6.3） |
| 店员后台 | 「客户管理」列表 / 详情 |

未登录顾客：**仍可** 扫码点餐、加菜、呼叫结账、付款——与现在完全一致。注册不是下单前提。  
**登录 = 可以用券；不登录 = 按原流程付款。** 同桌可以有人登录、有人不登录，互不影响。

注册引导规则：
- 引导只是提示，**不阻塞** 点餐和呼叫结账；关掉后本次会话不再反复弹。
- 有进行中的注册礼 / 邀请活动时，引导文案带上可得的券额。
- 在结账页注册成功 → 回到结账页，可直接给自己这一笔选刚领的券。

### 4.2 注册字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 名字 | **必填** | 展示名 |
| 手机号 | **必填** | 本店内唯一；登录主标识 |
| 生日 | **必填** | 日期；生日送礼见 §6.2 |
| NIF | 可选 | 有则按现有收款 NIF 规则校验 |
| 地址 | 可选 | 自由文本 |
| Email | 注册时 **可选**（已定） | 有则校格式并发验证邮件；本店内唯一。注册文案提示：**填写后可接收优惠券通知、找回密码**；同页提供「接收优惠通知」勾选（默认不勾，RGPD）。找回密码时若无邮箱则 **当场必填并绑定**（见 §4.5） |

### 4.3 登录（已定）

| 项 | 约定 |
|---|---|
| 主路径 | **手机号 + 自设密码**（不做短信 OTP 日常登录） |
| 邮箱 | 不作日常登录账号；用于找回密码 |
| 不做 | 短信/WhatsApp 日常 OTP（费用高；找回也不走短信） |

### 4.4 注册成功

1. 创建本店顾客档案（状态 `active`）
2. 若「注册送礼」开启且在活动期内 → 自动发一张注册券（§6.1）
3. 进入已登录态；可进「我的优惠券」

### 4.5 忘记密码（已定 · 邮箱）

成熟主方案：**邮件重置链接**（限时、一次性）。流程：

1. 顾客输入 **本店手机号**（认出账号）。
2. **档案里已有邮箱** → 页面 **带出该注册邮箱**（展示建议打码，如 `j***@gmail.com`，避免旁人偷看全称）→ 确认后发重置链接到该邮箱；顾客点开设新密码。
3. **档案里没有邮箱** → 邮箱变为 **必填**：顾客填写邮箱 → **先发验证邮件确认该邮箱可用** → 绑定到档案 → 再发（或同封）重置链接设新密码。  
   （避免别人拿你的手机号、填他自己的邮箱就把密码改走。）
4. 邮件收不到 / 仍无法自助 → **店员代重置**（核验后后台操作，记日志）。

其它规则：

- 重置链接短有效期（建议 15～60 分钟）、一次性、用后作废。
- 限流：同号 / 同 IP 请求频率上限。
- 对外文案避免泄露「该手机是否已注册」（可统一「若账号存在且可找回，我们已发送邮件」；**已登录态内的资料页**可明文显示自己的邮箱）。
- 发信 sole 通道见 §4.6（**不**用短信找回）。

### 4.6 事务发信方案（已定 · Resend + farvoo.com）

平台统一发找回密码 / 绑定验证邮件，**不**要求每店自备企业邮箱或自建 SMTP。

| 项 | 约定 |
|---|---|
| 服务商 | **Resend**（起步用 **Free**：约 100 封/天、3000 封/月；超额发失败 → 提示 + 走店员代重置） |
| 发信域名 | 已有根域 **`farvoo.com`**；现有业务二级域名不动，**另开专用二级域名**用于发信 |
| 推荐主机名 | **`mail.farvoo.com`**（Resend Domains 验证此主机；DNS 只加本组 SPF/DKIM 等，不影响现有站点二级域名） |
| 顾客看到的 From | 例如 `FARVOO <noreply@mail.farvoo.com>`（显示名实现时可 i18n；地址域名必须已验证） |
| Reply-To | 可选；需要时指向平台客服或该店对外邮箱（与 From 分离） |
| API Key | 仅服务端环境变量；禁止进前端 / 仓库 |
| 云端 | Web API 调 Resend 发信 |
| on-prem | 店机须能出网访问 Resend API；使用**同一平台域名与密钥策略**（不按店各绑一套 Resend 域）。出网失败 → 明确错误 + 店员代重置 |
| 不做 | 用个人 Gmail SMTP 当事务通道；每店自验 Resend 域名（v1）；短信/WhatsApp 发重置码 |

运维设置摘要（实现/上线检查单）：

1. Resend 账号 → Add Domain：`mail.farvoo.com`  
2. 在 `farvoo.com` 的 DNS 按 Resend 后台添加记录并 Verify  
3. 创建 API Key → 写入云端 / on-prem 密钥配置  
4. 应用发信一律 `from` ∈ `@mail.farvoo.com`

## 6. 发券活动（店内配置）

均在 **Ops 总闸已开** 的前提下，由店内配置。

### 6.1 注册送礼

| 配置项 | 说明 |
|---|---|
| 活动开关 | 开/关 |
| 活动时间窗 | 开始 / 结束；窗外不发 |
| 优惠金额 | 可配置 |
| 券有效期 | 发放日起 N 天，或固定截止日期（实现时定一种主写法） |
| 每人限领 | 同一顾客档案仅一次注册礼 |

### 6.2 生日送礼（已定）

| 配置项 | 说明 |
|---|---|
| 活动开关 | 开 → 到生日自动发；关 → 只存生日字段，不发 |
| 优惠金额 / 有效期 | 可配置（与注册礼同类） |
| 每人每年 | 同一自然年（或 Lisbon 营业年，实现时定）同一顾客最多一张生日券 |

**定时任务（已定）**：复用现有 **唯一夜间任务** `/api/cron/nightly-close-sessions`（云端 Vercel Cron + on-prem 日切同源）。在该任务内增加「生日发券」步骤：扫开启了总闸且开启了生日送礼的店，给当日生日且本年未领过的顾客发券。  
**禁止**再新开第二条独立 cron 专跑生日。

### 6.3 邀请注册（新增）

| 项 | 约定 |
|---|---|
| 谁能邀请 | 本店已注册、`active` 的顾客 |
| 邀请方式 | 「邀请好友」页生成 **本人专属邀请链接**（可复制 / 系统分享 / 二维码），只在本店有效 |
| 被邀请人 | 打开链接 → 本店注册页（带邀请人标记）；**必须是新手机号**，已注册的不算 |
| 奖励 | 活动开启时：**被邀请人注册成功即得券**；**邀请人在被邀请人首次在本店成功结账后得券**（防刷假号；已定） |
| 配置 | 活动开关、时间窗、邀请人面额 / 有效天数、被邀请人面额 / 有效天数、每位邀请人奖励上限（可选） |
| 限制 | 自己邀请自己无效；一人只能被邀请一次（以第一个有效邀请为准） |
| 活动关 | 链接仍可打开注册，但不发邀请券；注册礼照常按 §6.1 |

被邀请人可 **同时** 拿注册礼与邀请礼（两个活动各自开关）。

### 6.4 主题活动（新增）

平台内置一批 **主题模板**（名称三语 + 建议日期 + 建议面额），如：新年、情人节、复活节、母亲节、圣安东尼节（Santos Populares）、父亲节、圣诞节。

| 操作 | 说明 |
|---|---|
| 激活 | 从模板一键生成本店活动（带入名称、日期、面额，可改） |
| 编辑 | 改名称、活动日期、面额、券有效期、发放对象 |
| 创建 | 不用模板，店里自建主题活动 |
| 停用 | 停止后续发放；已发的券不收回 |

发放对象：

| 方式 | 说明 |
|---|---|
| 全体 | 本店全部 `active` 会员 |
| 选择 | 店员勾选指定会员 |

发放时机：店员点「发放」立即发；或设定在活动开始日由夜间任务自动发（同一 nightly，不另开 cron）。  
发放后 **邮件通知** 收到券的会员（见 §6.5）。  
**同一活动同一顾客最多一张**（重复点发放不会重复发）。活动期间新注册的会员，可在活动页「补发给新会员」。

### 6.5 发券邮件通知（新增）

| 项 | 约定 |
|---|---|
| 通道 | 同 §4.6：Resend + `@mail.farvoo.com` |
| 发给谁 | 有 **已验证邮箱** 且 **同意接收优惠通知** 的会员；无邮箱 / 未同意的不发，券照发 |
| 何时发 | 主题活动发放、生日券、邀请人得券时；注册 / 被邀请注册得券在页面直接显示，不另发 |
| 内容 | 店名、券面额、有效期、「我的优惠券」链接；zh / en / pt 按会员语言 |
| 退订 | 每封带一键退订链接（RGPD 必须）；退订后只停通知，不影响券与找回密码邮件 |
| 额度 | 群发会远超 Resend Free（100 封/天）→ 上线前须升级付费档；超额发送失败不影响发券 |

规则（以上所有活动共用）：

- 活动关或总闸关：不发。
- 已发出的券不因活动关闭或编辑而收回、不改面额（作废走 §7）。

## 7. 优惠券模块（店员 / 店主运营）

### 7.1 券的概念

| 层 | 含义 |
|---|---|
| 发放来源 | 注册礼 / 生日礼 / 邀请礼 / 主题活动 / 店员手动发放 |
| **顾客持有券（券实例）** | 唯一 id、面额快照、到期日、状态、所属顾客 |

### 7.2 店员操作

| 操作 | 说明 |
|---|---|
| 发放 | 指定顾客 + 面额 + 截止日期（或有效天数） |
| 作废 | 未使用可作废；已核销不可作废 |
| 查看 | 按顾客 / 状态 / 到期筛选 |

### 7.3 券实例状态

```text
issued（可用）
  → redeemed（已核销，绑定某次收款）
  → voided（作废）
  → expired（过期；使用时校验；夜间任务可顺带标记）
```

硬规则：

1. **一券一次核销**
2. 核销仅在确认收款 **成功写台账之后**；选券不算核销
3. 面额与到期以发放时快照为准
4. 作废 / 过期 / 已用 不可再选
5. **每一笔收款最多 1 张券**（整桌 = 一桌一张；均摊 / 按菜 = 每份 / 每票各一张）

### 7.4 使用规则（已定）

| 规则 | 约定 |
|---|---|
| 门槛 | **无最低消费门槛**（默认）；券可抵到实收为 0 |
| 券面额 > 本笔应付 | **允许选**；抵扣额 = min(券面额, 本笔应付)；**不找现** |
| 券数量 | **每笔收款仅 1 张** |
| 与员工折扣率 `discount_rate` | 店内 **开关二选一**：**互斥** 或 **同用**（见 §7.5） |

### 7.5 券与员工折扣：互斥 / 同用（已定）

店内配置一项（总闸开后可见），例如「优惠券与整单折扣」：

| 模式 | 行为 |
|---|---|
| **互斥** | 本笔已选券 → 不可再应用员工折扣率；已应用折扣率 → 不可再选券（或选券时清空折扣——实现时 UI 须说清，避免静默丢折扣） |
| **同用** | 允许同时有券与 `discount_rate` |

**同用时扣减顺序（已定，唯一口径）**：

```text
折前应付
  → 先减优惠券抵扣（最多抵到 0）
  → 再对剩余金额应用员工折扣率
  → 得到实收（≥ 0）
```

> 注意：这与当前「仅 `discountRate` 打在折前应付上」的路径不同；实现时须改收款目标金额的 **sole** 计算，禁止两套公式并存。

## 8. 结账关联使用（已定）

### 8.1 谁选券

| 角色 | 行为 |
|---|---|
| **呼叫结账人（已登录）** | **呼叫结账时** 从自己账户选 0 或 1 张券 |
| 员工（结账页） | 呼叫后可换券 / 去掉券，**只能从呼叫结账人的账户里选**；确认收款成功后核销 |
| 未登录呼叫 | 这一笔不能用券 |

**每一笔收款最多一张券，以这一笔的呼叫结账人账户为准。**

- **按菜多人呼叫**：每人呼叫自己那一票时各选自己账户里的券，互不影响。
- **结账页 · 分单详情**：每一行（座位 / 票）标出是否用券；用券的那一行显示「优惠券 −€X」（员工端另显示券主人名字；顾客端不显示是谁的券）。

**核销时机**：仅在确认收款成功写入台账之后 → `redeemed`。取消/失败 → 券仍可用。

### 8.2 与分单模式

| 模式 | 约定 |
|---|---|
| 整桌 `whole_table` | 只有 1 笔 → 全桌 1 张，抵整桌 |
| 均摊 `even` | 每份最多 1 张；v1 只有呼叫结账的那个人能用券（抵他自己那一份，由他或员工指定是哪一份） |
| 按菜 `by_item` | 每票最多 1 张，各用各票呼叫人的账户；金额与 [`by-item-collect-payment.zh.md`](./by-item-collect-payment.zh.md) 对齐（在 sole 金额公式中纳入券，见 §7.5） |

券绑到 **具体一次收款义务**，禁止错票核销。

### 8.3 金额与票面 / IVA（已定：跟行业与现有折扣口径）

对齐 [`collect-payment-receipt-iva.zh.md`](./collect-payment-receipt-iva.zh.md) 与葡萄牙餐饮常见做法：

1. 小票 / 发票上 **单独列出优惠券抵扣行**（名称 + 抵扣额），对账能看清。
2. **实收** = 该笔应付按 §7.5 扣完后的金额（≥ 0）；券不产生找零现金。
3. **税基按折后（含券抵与员工折扣后）含税应付** 处理，与现有「折扣反映在营业额 / FS·FT 门槛用折后金额」一致；不把券做成「账外礼品、税基仍按全价」的旁路。
4. 台账能区分：折前应付、券抵、员工折扣、实收。

实现阶段对照现有 `discount_rate` 出票与 bill_sync 字段扩展，不另发明第二套税务故事。

### 8.4 客人身份怎么区分（全局 · 已定）

扫码手机上是**两套身份**，不要混成一套：

| 套 | 是什么 | 干什么 |
|---|---|---|
| 手机编号 | 本机保存的 `guest_client_id` | 点菜、按菜呼叫「哪台手机」、账单实时刷新 |
| 会员登录 | 本店会员 cookie → `customer_id` | 注册/登录、我的优惠券、结账选券 |

**怎么判断已登录 / 未登录：** 问顾客账户接口（如 `me`）——有会员就是已登录，没有就是未登录。

**Realtime（账单/开台刷新）怎么保证不被登录弄坏：**

- 刷新一直用现在的游客客户端 `createGuestClient`（anon），**登录、登出都不许换成别的 Supabase 客户端去订同一桌**。
- 会员和券只走顾客 HTTP API（服务端认会员 cookie），不走游客 Realtime 客户端，也不为了会员去放宽桌上那套 anon 读权限。

细则见技术方案 [`../technical/customer-coupons-tech-plan.zh.md`](../technical/customer-coupons-tech-plan.zh.md) §1.1。

用券仍以「这一笔的呼叫结账人账户」为准（§8.1）；未登录呼叫 → 这一笔不能用券。员工按手机号代查是否上 v1：仍可后置（上表方案 B）。

# 本次改动业务场景测试报告：按菜分单恢复点单，已有收款时只清退当前票

日期：2026-10-10 · 分支：`fix/by-item-unlock-keep-queue` · 环境：本地 :3002（worktree，`.next-uat`）+ 本地 Docker Supabase · 测试店：白云 `restaurant-mohnrib5`

## 1. 本次修改

- **问题**：上一版（`4a67c002`）里，员工对某张未付票点「恢复点单」后，只要这桌已没有「已呼叫且未付」的票，就清掉接管标签，整桌退出结账队列。哪怕这桌已经有人付过钱，员工也没法继续对这桌收款。
- **改动**：新迁移 `20261010200000_by_item_unlock_keep_queue_when_collected.sql`，只改 `individual_checkout_apply(unlock)` 里清标签的条件：**没有已呼叫未付票，并且这桌从未收过款**，才清标签、放开这桌；已有收款则保留标签，这桌继续留在结账队列。
- 文档同步：`ai-schema.md`、`guest-individual-checkout.zh.md`、`AGENTS.md`。
- **客人手机端：代码不改。** 约定的行为是：呼叫时本地草稿即清空，恢复点单后可重新点单、重新分菜（本次实测确认）。
- **不在范围**：整桌、均摊；收款按票编号记账；员工端结账页。

## 2. 核心业务规则（不变量）

1. 恢复点单只删当前这张未付票，已付票和别人的票不动。【已实现，上一版】
2. 这桌**已有收款**：恢复点单后分单仍是结账中，标签保留，员工可继续对这桌收款。【本次新增】
3. 这桌**从未收款**，且没有其他已呼叫未付票：恢复后分单回到已确认，整桌退出队列。【已实现，上一版】
4. 被删票的菜回到剩余菜品，其他手机可以认领。【已实现，上一版；本次手机侧实测】

## 3. 详细测试场景

### 场景 1：数据库层对照（事务内构造，回滚）
- **前置**：A 已付并有收款流水、B 未付已呼叫，标签已贴；另一套 C 单独未付、无任何收款，标签已贴。
- **操作**：分别解锁 B、解锁 C。
- **预期**：有收款的：删 B 后 `requested` + 标签保留，结果只剩 A；无收款的：删 C 后 `confirmed` + 标签清空。
- **结果**：【已验证】pass（`requested | t | A:true`；`confirmed | f`）。

### 场景 2：有收款时恢复点单（原场景）
- **前置**：VIP888 开台。客人手机 Jj 呼叫第 1 张，员工收款；Jj 再呼叫第 2 张。分单 `requested`、标签已贴。
- **操作**：员工恢复点单（第 2 张）。
- **预期**：第 2 张票消失；已付的 Jj 和收款记录不变；分单仍 `requested`；这桌仍在队列。
- **结果**：【已验证】pass。库内 `requested | 标签 t | Jj:true`；`GET checkout/requests` 中该分单 `inQueue=true`。

### 场景 3：没收款时恢复点单
- **前置**：VIP999 开台，一张未付呼叫票，无任何收款。
- **操作**：员工恢复点单。
- **预期**：这桌退出队列；分单 `confirmed`；标签清空；结果为空。
- **结果**：【已验证】pass（`inQueue` 由 true 变为 false；`confirmed | f | 0`）。

### 场景 4：恢复点单后，客人手机读到的状态
- **前置**：场景 2 之后；另一台手机（Kk）呼叫了一张冰水票。
- **操作**：刷新原手机的账单页。
- **预期**：这台手机不再被锁；被删票的 001 中水回到可认领（剩余 2）；已付的 Jj 显示「已结清，不可改」；Kk 的认领照常显示；这台手机的选择从空白开始，可重新分。
- **结果**：【已验证】pass（页面文字逐项符合）。

### 场景 5：手机端不刷新页面，实时变化
- **操作**：手机账单页保持打开，员工恢复点单，观察页面是否自己从「暂时不能点单」变化。
- **结果**：【未验证】。测试时 Browser 面板处于隐藏状态（`visibilityState=hidden`），页面不跑实时刷新。用对照确认这是环境限制，不是本次改动：另一台手机呼叫新票，该页面同样没有更新。解锁时确实写入了 `silent/unlock` 通知（库内已查到），手机收到任何通知都会 `refreshBill()`（代码已核实）。需要在前台显示的面板里补测。

### 覆盖维度说明
- 本地与服务端：手机刷新后以服务端为准（场景 4）。【已验证】
- 同时恢复同一张票、已部分收款的票拒绝恢复：上一版已测，本次函数其余逻辑未改。【已验证（上一版）】
- 整桌、均摊：本次只改 by_item 解锁分支，未再跑。【未验证】
- 转台、并台、历史遗留 `unlocked` 票：未改，未测。【未验证】

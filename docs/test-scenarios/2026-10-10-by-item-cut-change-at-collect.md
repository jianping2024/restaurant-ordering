# 本次改动业务场景测试报告：按菜分单「基数」员工改动只在收款时才作数

日期：2026-10-10  
分支：`feat/by-item-cut-change-at-collect`  
UAT 基址：`http://localhost:3002`（功能分支，非 `:3000`；`MESA_NEXT_DIST_DIR=.next-uat`；本地 Docker Supabase；餐厅 `restaurant-mohnrib5`）

> 名词：「基数」= 一道菜的分数份额按几分之一切（1/2、1/3、1/4、1/5）。同一道菜只有一种基数。

## 1. 本次修改

- **内容**：员工草稿里改一道菜的基数，**只在点「收款」那一次写入服务端时才作数**；其余员工写入（例如恢复点单前的落库、其他路径的按菜落库）**不许改变服务端已有的基数**。
- **改动点**：新增判断 `fractionCutChangedLineKeys`（唯一模块 `by-item-fraction-unit.ts`）；`submitCheckoutRequestForTable` 新选项 `allowCutChange`；接口 `POST …/checkout/request` 新字段 `allow_cut_change`（仅员工、仅收款那次写入传）；新错误码 `by_item_cut_change_at_collect`（409 + `line_keys`）；员工页 toast 文案；文档与 AGENTS.md。
- **角色 / 页面**：员工结账页（`/dashboard/checkout` 按菜）、顾客手机账单页（提示不变，复测）。
- **不动**：金额算法；顾客呼叫路径；已收款份额锁基数的逻辑；整桌 / 均摊。

## 2. 核心业务规则

1. 【已实现】基数以**第一个已呼叫结账的客人**为准；后面的客人提交冲突 → 拒绝（409 `by_item_unit_mismatch`），手机端精确定位到那道菜并提示。
2. 【已实现】员工草稿（池子里分的、右侧退回重分的）只在员工本地，**不占位**；别的客人仍按服务端基数校验。
3. 【本次新增】员工想把服务端已有基数换成新的：**只有收款那次写入**允许（`allow_cut_change`）；其它员工写入改了已有基数 → 拒绝 `by_item_cut_change_at_collect`。
4. 【已实现】收款后，收下的分数份额把基数固定；之后客人和员工再换基数都被拒（`by_item_unit_mismatch`）。
5. 【已实现】这道菜**还没有任何分数份额**时，员工第一次分的基数不受第 3 条限制，写入后生效，收款后固定。
6. 【已实现】员工收的那一票在这道菜上只是整份 → 没有分数份额 → 基数不固定（用户确认：保持）。
7. 【已实现】员工写入后，这道菜上所有份额必须是同一基数，否则 `by_item_unit_mismatch`；所以换基数时员工要把这道菜上所有人的份额都重分。

## 3. 详细测试场景

> 角色：甲/乙…=顾客手机（无登录，`guest_client_id`）；员工=`qiantai1`。菜 101 Blue Lagoon（2 份）、102 Mojito（1 份）、自助餐 1 位成人。每个场景用独立测试台。

### 场景 1：员工草稿换基数，但不是收款那次写入
- **前置**：甲已按 1/2（单位 2）呼叫结账，服务端方案里甲 1/2。
- **操作**：员工（非收款写入）把甲的份额写成 1/3。
- **预期**：拒绝，错误码 `by_item_cut_change_at_collect`，`line_keys` 指向 101。
- **数据验证**：方案仍是甲 1/2（单位 2），未被改。
- **异常恢复**：员工放弃，或在收款时才改。
- 结果：【已验证】（N1、N1b）

### 场景 2：员工草稿期间，别的客人提交（草稿不占位）
- **前置**：同场景 1，员工在结账页只改了草稿（未写入）。
- **操作**：乙按 1/2 呼叫 → 通过；丙按 1/3 呼叫。
- **预期**：乙通过；丙被拒 `by_item_unit_mismatch`（基数仍是甲的 1/2）。
- **数据验证**：方案里是甲 1/2、乙 1/2。
- 结果：【已验证】（N3、N3b）

### 场景 3：员工在收款那次写入换基数（API）
- **前置**：甲、乙都按 1/2 已呼叫。
- **操作**：员工收款写入（`allow_cut_change`），把甲、乙的份额都改成 1/3。
- **预期**：通过；之后客人按旧 1/2 被拒、按新 1/3 通过。
- **数据验证**：方案里全是单位 3。
- 结果：【已验证】（N2、N2b）

### 场景 4：收款写入只改了一部分份额，这道菜混了
- **前置**：甲、乙都按 1/2 已呼叫。
- **操作**：员工收款写入，只把甲改 1/3，乙留在 1/2。
- **预期**：拒绝 `by_item_unit_mismatch`，员工要把这道菜上所有人都重分。
- 结果：【已验证】（N2c）

### 场景 5：员工在界面上真实操作：改基数 → 收款 → 基数固定
- **前置**：甲按 1/2 呼叫；员工打开结账页，按菜。
- **操作**：员工点甲份额行的 `‹ 1/2份` 退回池子 → 池子这道菜重新自由 → 点 `1/2份` 出小条，选 1/3 → 甲份额变 `1/3 × €3.95 = €1.32` → 点「收款」→ 确认现金。
- **预期**：收款成功；甲已付 €1.32。
- **数据验证**：方案里甲 `1/3`、单位 3、`locked_amount=1.32`、已付；这道菜基数固定为 1/3。
- **后续**：乙按 1/2 → 拒绝；乙按 1/3 → 通过；员工再把别人的份额改成 1/4 并收款 → 拒绝（已有已付 1/3）。
- 结果：【已验证】（N5a~N5d；界面收款走的是 `allow_cut_change`）

### 场景 6：员工草稿未写入时，服务端不变（界面）
- **前置**：甲 1/2 已呼叫；员工页里把甲退回、改成 1/3，但还没点收款。
- **预期**：服务端方案仍是甲 1/2（单位 2）。
- 结果：【已验证】（N8a）

### 场景 7：恢复点单（单张票解锁）与员工草稿
- **前置**：同场景 6，员工草稿 1/3，点甲票旁的「恢复点单」。
- **预期（实际）**：甲的票变「未呼叫」（可以重新点单、改认领），**员工草稿被丢弃，方案仍是 1/2**；这个入口只做解锁，不把草稿落库。
- **数据验证**：`individual_tickets` 里甲 `state=unlocked`，方案 persons 仍是 1/2（单位 2）。
- 结果：【已验证】
- 说明：因此"恢复点单前的落库"在按菜单张票解锁这个入口并不存在；本次的限制是对**其它非收款的员工按菜写入**的保护（例如整单恢复前的落库、`persistPrunedByItem`、均摊/整桌落库路径误带按菜数据）。这部分只做了接口层验证（场景 1），界面上没有稳定的入口可点。【未验证：界面入口】

### 场景 8：还没有任何客人定基数，员工先分
- **前置**：没有客人呼叫过这道菜的分数份额；员工结账页自己分。
- **操作**：员工写入这道菜 1/3（非收款写入）。
- **预期**：通过（不受第 3 条限制）。
- 结果：【已验证】（N4）

### 场景 9：员工把分数份额全部退回，写入
- **前置**：甲 1/2 已呼叫。
- **操作**：员工把甲的份额改回整份 1，写入。
- **预期**：通过（这道菜不再有基数）。
- **风险**：之后员工再写一次新基数，等于换了基数；我没有堵（见第 5 节）。
- 结果：【已验证】（N7）

### 场景 10：手机端精确定位与提示
- **前置**：顾客手机本机已认领 101 的 1/2（草稿），第一个客人先按 1/3 呼叫。
- **操作**：手机点「呼叫结账」（停在旧状态）。
- **预期**：服务端拒绝；toast「有菜品已按别人先定的分法分，已标出，请重新认领」；101 菜卡标红并自动展开，写明「这道菜已按 1/3 分，你认领的份数对不上，请重新认领」；单位选择只剩「1」和「1/3」且 1/3 选中；已有认领保留。
- 结果：【已验证】（浏览器 375×812）

### 场景 11：回归
- 未碰的菜 / 旧混分方案：别的菜正常呼叫（S7a）；员工写入没动过混分的菜不被拦（S7c）；动了才拦（S7d）。【已验证】
- 空菜首个客人定基数、第二人冲突被拒、跟随通过、整份不受影响、2/4 与 1/4 同基数通过、1/2 与 1/4 不同基数被拒（S1~S6）。【已验证】
- 已收款份额锁基数；客人、员工改基数被拒（S9）。【已验证】
- 旧页面不带单位、越界单位（C1~C4）。【已验证】
- 顾客整桌、均摊呼叫（R1、R2）。【已验证】
- 员工不改基数的写入：在别的菜加整份通过；原样再存一次通过（N6、N6b）。【已验证】
- 员工页：1份/1/N份顺序、分法小条、退回按钮、垃圾桶 44px、买断 `‹ 1A/‹ 1C`（上一轮验证，本次未改这些代码）。【已验证（上一轮，同代码）】

### 场景 12：并发 / 断网 / 重复提交
- 真正同时提交（两台手机同一毫秒呼叫）：服务端呼叫带版本号并在失败后重读重试（读代码确认），本次没有做真并发压测。【未验证】
- 断网、超时后重试：被拒的写入不留部分数据（N1b 证明被拒不落库）；断网/超时场景本身没有实测。【未验证】
- 手机本地草稿被他人先定的基数打断后的恢复：改成 1/3 再呼叫成功（上一轮验证）。【已验证（上一轮，同代码）】

## 5. 风险与待确认

- **「恢复点单」界面入口不落库**：本次限制保护的是接口层的其它非收款写入；单张票解锁本身不写草稿（场景 7）。如果你期望解锁时也把员工草稿落库，需要另行确认设计。【待确认】
- **员工清空分数份额后再写新基数**（场景 9）：等于绕过限制两步换基数，我选择不堵，因为堵了员工就没办法删客人的错误认领。【设计建议，未批准】
- **并发与断网**：未做真并发与断网压测（场景 12）。【未验证】
- 清冗余：新判断复用 `fractionUnitOfLine` / `fractionUnitConflict` / `fractionUnitQty`；与已有 `changedFractionLineKeys`（限定校验范围）语义不同，不是平行写法。

# 本次改动业务场景测试报告：关台后最终分单读取

日期：2026-10-12  
分支：`fix/guest-bill-settled-final-read`  
UAT 基址：`http://localhost:3002`  
店：白云 `restaurant-mohnrib5`，桌 A-18，账号 `baiyun@gmail.com`（开台、收款、关台）

## 1. 本次修改

- **问题**：最后一笔收款在同一个事务里关桌，顾客页只冻结关桌前最后一屏，所以最后付款的人永远没有「已收款」，汇总里还留着「已呼叫结账」，且与「本桌已结清」互相矛盾。
- **修法**：页面记住最后见到的活会话号；桌关了之后带 `closed_session_id` 读一次该已关闭会话的最终分单、收款和票，重算页面。标题按有没有未付清的票选「已结清」或「已关台」。
- **文件**：`customer-bill-context.ts`、`customer-session-context.ts`、`customer/bill/route.ts`、`request-customer-context.ts`、`customer-bill-sync.ts`、`use-customer-bill-read-model.ts`、`BillPage.tsx`、i18n 四个文件、文档三处、本报告。

## 2. 核心业务规则

1. 【本次新增】关台后页面用已关闭会话的最终分单/收款/票重算，不再冻结关台前那一屏的收款状态。
2. 【本次新增】只有本桌的已关闭会话才返回数据；会话号不对或不是这张桌子的 → 空。
3. 【本次新增】关台后所有票都已收款 → 「本桌已结清」；还有票没付清 → 「本桌已关台，如有账单疑问请联系服务员」，没付的人如实显示未付。
4. 【已实现】订单明细仍然冻结，不重读。

## 3. 详细测试场景

### 场景 1：最后一人付款关桌 【已验证】

- **前置状态**：A-18 开台（自助餐 + 冰水 ×2）。Ana（冰水 + 自助餐 €16.80）、Bruno（冰水 €1.85）依次按菜呼叫；收银员收 Ana。以 Bruno 手机打开账单页，停在待结账页。
- **操作过程**：收银员收 Bruno €1.85（最后一笔，自动关台）；手机回到前台。
- **预期结果**：标题「本桌已结清，欢迎下次光临」；总计 €18.65、已收款 €18.65；Bruno「我 · 已收款」、Ana 已收款；没有「已呼叫结账」行、没有菜品清单。
- **数据验证**：库里会话 `closed`，`bill_splits.status = paid`，两笔收款；接口带会话号返回 paid 的分单。
- **异常恢复**：桌已关。

### 场景 2：强制关台，Bruno 没付 【已验证】

- **前置状态**：同场景 1，收了 Ana，Bruno 未付。
- **操作过程**：员工强制关台；Bruno 手机回前台。
- **预期结果**：标题「本桌已关台，如有账单疑问请联系服务员」；已收款 €16.80、已呼叫结账 €1.85；Bruno「我」未付，菜品清单仍在；Ana 已收款。
- **异常恢复**：桌已关。

### 场景 3：接口只给对的人 【已验证】

- 带正确会话号 → 返回最终分单、2 笔收款、2 张票（Bruno `mine`）；错误会话号 → 空；不带 → 空。

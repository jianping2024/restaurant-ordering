# 楼面自助餐改人数：仅加减（不可输入）

日期：2026-10-22  
分支：`fix/buffet-guest-count-stepper-only`

## 1. 本次修改

- **内容**：楼面改自助餐成人/儿童人数，中间数字只读，只能点 − / +；开台表单与已开台详情同一套 `BuffetGuestCounter`。
- **文件**：`WaiterTableDetailLayout.tsx`（`BuffetGuestCounter`）、`WaiterBuffetPackagesEditor.tsx`、`docs/agent-sole-index.zh.md`
- **角色 / 页面**：前台/楼面 → 楼面看板 → 开台人数 / 桌详情人数
- **未改**：`POST …/staff/waiter/buffet`、已开台自动保存、购物车等别处的可输入 `CartQtyStepper`

## 2. 核心业务规则

1. 【本次新增】楼面自助餐人数唯一 UI：`BuffetGuestCounter` = − / 数字展示 / +，禁止中间格输入。
2. 【已实现】已开台人数仍经 `useWaiterBuffetOpenMutation` 防抖自动 `intent=save`。
3. 【已实现】冷开台仍要显式确认后 `intent=open`。
4. 【设计建议·未采纳】空失焦恢复原值——本次不保留输入，故不适用。

不变量：不得再出现「点中间格清空 → 失焦变 0 → 自动保存写库」这条路径。

## 3. 详细测试场景

### 场景 1：已开台详情 — 中间数字不可输入，加减可改人数

- **前置状态**：白云测试店；某桌已开台且自助餐成人 ≥ 1；员工已登录楼面
- **操作过程**：打开该桌详情 → 点成人中间数字 → 再点 − / +
- **预期结果**：中间不是可聚焦输入框；− / + 后人数变化并自动保存
- **数据验证**：操作日志可出现正常「改人数」；不应因「点数字框」单独写出 `→0`
- **异常恢复**：刷新详情后人数与服务端一致

### 场景 2：开台表单 — 同样只加减

- **前置状态**：空闲桌；有可用自助餐套餐
- **操作过程**：开台 → 成人/儿童只用 − / + → 确认开台
- **预期结果**：中间不可输入；确认后会话人数与步进结果一致
- **数据验证**：开台审计人数与 UI 一致
- **异常恢复**：取消开台不留下半开会话（沿用原开台行为）

### 场景 3：回归 — 购物车数量仍可输入

- **前置状态**：顾客/点菜侧购物车有可编辑数量行（沿用既有 `CartQtyStepper`+`onQtyChange`）
- **操作过程**：点购物车行中间数量并改数
- **预期结果**：仍可输入（本改动不波及购物车）
- **数据验证**：不适用楼面人数 API
- **异常恢复**：不适用

### 场景 4：连点 − 减到 0（已知产品取舍）

- **前置状态**：已开台成人 ≥ 1
- **操作过程**：连点 − 直到 0
- **预期结果**：仍可到 0（本次不禁止减到 0）；路径是加减，不是输入清空
- **数据验证**：操作日志可为 `→0`，但详情应能对应到步进，而非空失焦
- **异常恢复**：再点 + 可改回

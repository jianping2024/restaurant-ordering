## 1. 本次修改

- **内容**：顾客手机账单页选「按菜」后的认领界面改版，解决三个反馈：选了份量不知道下一步点 +；累计金额看不懂；忘了填名字。
  - 份量按钮 `+1 / +1/2 … +1/5` 本身就是「加」，点一下加到本机名下，不再有「先展开 → 选大小 → 再按 +」；`−` 撤回上次加的那种。
  - 每道菜显示单价、剩余、我的份数和我的金额。
  - 新增「全桌认领进度」：我 / 其他人 / 待认领，三个金额加起来等于全桌。「全部认领」改为「剩下的 €X 都算我」。
  - 名字是第 ① 步，必填，填好变 ✓。底栏改为账单摘要 + 一个主按钮：先认领菜品 → 填写名字 → 呼叫结账。点「填写名字」滚到名字栏、聚焦并标红。
  - 其他人卡片的状态位：已呼叫结账（灰）→ 已结清（绿），同一个位置，不新增行。
  - 排版收紧（同日追加）：菜名独占一行，单价并入灰字「€2.50 / 份 · 还剩 3」；份量按钮只留一行 `+1 / +1/2 …`（去掉「一整份 / n 人分」副标，高 44px）；底栏摘要独占一行（左「谁的账单 · n 道菜」、右金额），下面整宽主按钮，再下面「返回点单」。
- **文件**：`GuestClaimDishCard.tsx`、`GuestClaimPanel.tsx`、`GuestBillBottomDock.tsx`、`BillPage.tsx`、`guest-claim.ts`（新增 `guestClaimLineAmounts` / `guestClaimMoney` / `guestClaimForDisplay`）、`use-guest-claim.ts`、`guest-claim.test.ts`、`messages.ts` + `messages-de/es/fr.ts`、`AGENTS.md`、5 份产品/设计文档、本报告。
- **角色 / 页面**：顾客手机 `/{slug}/bill?table_id=…`，按菜模式。整桌 / 均摊模式的底栏没改。「已呼叫」页面只是共用同一个底栏组件（只传返回按钮）。
- **不改**：数据库、接口、分单规则、`buildMyTicket` 呼叫载荷、冲突与分法锁定的服务端规则。

## 2. 核心业务规则

1. 【本次新增】每道菜「我的 €」与底栏金额同源：同一个分钱函数 `allocateByItemShareAmounts`，各道菜相加等于呼叫金额（到分）。不用「单价 × 份数」各自四舍五入。
2. 【本次新增】全桌 = 我 + 其他人 + 待认领（到分），待认领不小于 0。
3. 【本次新增】没填名字时可以预览金额（用占位名字算），但呼叫载荷 `buildMyTicket` 仍为空，不会提交一张没名字的票。
4. 【已实现】一道菜只能有一种分法：一旦有人先选了 ⅓，其他人这道菜只剩「+1」和「+1/3」。
5. 【已实现】同一份菜被别人抢先呼叫后，本机呼叫会被拒绝、页面刷新、该菜标红、呼叫按钮禁用。
6. 【已实现】别人收款后卡片不可改（已结清）。
7. 【已实现】认领草稿只存在本机，别人只能看到已呼叫结账的人。待认领包含「别人还在选、你看不到」的部分。

## 3. 详细测试场景

### 场景 1：份量按钮即加，金额立刻出现 【已验证】
- **前置状态**：A-20 开台，自助餐 2 成人 1 儿童 + 冰水 ×1（€1.85）+ Imperial ×2（€1.95）。手机 A（`localhost`）选「按菜」，没填名字。
- **操作过程**：点冰水的「+1/3」。
- **预期结果**：冰水卡出现「这道菜按 3 人分」，「我的 1/3 份 €0.62」；我 €0.62、待认领 €55.03；底栏摘要行「还没填名字 · 1 道菜」右侧 €0.62，按钮「填写名字」。
- **数据验证**：页面文字逐项核对。冰水按钮只剩 `+1`（灰）与 `+1/3`。
- **异常恢复**：见场景 2。

### 场景 2：份量加减与分法释放 【已验证】
- **操作过程**：冰水依次 +1/3 → +1/3 → 按 −、−、−。
- **预期结果**：⅓ €0.62 → ⅔ €1.23 → 1 份 €1.85（`+1/3` 变灰）→ ⅔ → ⅓ → 0（卡片回到五个份量按钮，分法释放）。
- **数据验证**：几步金额与「全部归一人时 €1.85」一致。

### 场景 3：忘填名字 → 底栏引导 → 回到名字栏 【已验证】
- **前置状态**：场景 1。
- **操作过程**：点底栏「填写名字」。输入「张三」，按键盘 Return。
- **预期结果**：页面滚到名字栏，输入框聚焦、红框，红字「先填名字，才能呼叫结账」；此时底栏按现有规则被 CSS 藏起。输入后红字消失、名字 ① 变 ✓。Return 后失焦，底栏回来：「张三 的账单 · €0.62 · 1 道菜」+「呼叫结账」。
- **数据验证**：Browser pane 取元素：`activeElement` 就是名字框、`aria-invalid=true`、边框红；失焦后 `[data-guest-call-checkout-dock]` 显示恢复。iOS 模拟器 Safari 上同样完成：聚焦、红框、红字、页面滚动、Done 收键盘后底栏恢复。
- **异常恢复**：模拟器里有一次「点完 CTA 立刻打字，字没进框」（`text` 工具报输入了 3 个字符，框仍为空），随后手动点框再打字正常；另一轮重做「点 CTA → 立刻打字」则正常进入。第一次现象**没有复现**，原因未证实（模拟器输入时序或真问题，无法区分）。

### 场景 4：各道菜金额相加 = 底栏 = 服务器票金额 【已验证】
- **操作过程**：手机 A：自助餐 +1 成人、冰水 +1/3、Imperial +1/3，呼叫结账。
- **预期结果**：每道菜：成人 €19.95 + 冰水 €0.62 + Imperial €0.65 = €21.22；底栏 €21.22。
- **数据验证**：呼叫后页面显示分单结果「张三 €21.22」。SQL：`bill_splits` 该单 `split_mode=by_item`、`status=requested`、`result[0].amount=21.22`，`persons` 里的冰水 / Imperial 份额带 `qty_unit_den:3`。
- **自动化**：`guest-claim.test.ts` 用三个名字（Ann / Me / Zed，保证至少一个名字拿到零头 1 分）验证「逐道菜相加到分 = `buildMyTicket.amount`」，并断言这个用例不是空测。

### 场景 5：另一台手机看到别人，数字对得上 【已验证】
- **前置状态**：场景 4 之后。手机 B（`127.0.0.1`，独立本地存储）打开同一桌，选按菜。
- **预期结果**：「其他人已认领」出现「张三 €21.22 · 已呼叫结账（PT：Pediu a conta）」；进度条：我 €0.00、其他人 €21.22、待认领 €34.43（= €55.65 − €21.22）；冰水 / Imperial 只剩 `+1` 与 `+1/3`，带「这道菜按 3 人分」。
- **数据验证**：页面文字 + 全桌 €55.65 与账单明细合计一致。

### 场景 6：手机 B 认领并呼叫，金额随别人变化 【已验证】
- **操作过程**：手机 B 填「李四」，冰水 +1/3、自助餐 +1 成人，呼叫。
- **预期结果**：李四 = 成人 €19.95 + 冰水 €0.61 = €20.56（冰水已有两个 ⅓，合计 €1.23 在两人之间 62 / 61 分）；呼叫后 `bill_splits.result` 有张三 €21.22、李四 €20.56。
- **数据验证**：SQL 读 `result`。

### 场景 7：收款后状态位换样式，不新增行 【已验证】
- **操作过程**：收银员（owner）对张三（`person_index 0`，`party_id` 带上）`confirm-payment`，现金 €21.22。手机 C（`[::1]`，第三台）打开。

### 场景 8：别人抢先呼叫，本机手机过期状态下呼叫 【已验证】

### 场景 9：剩下的都算我，刷新后草稿还在 【已验证】

## 5. 风险与待确认

- **iOS 软键盘 + 程序滚动**：「填写名字」会 `scrollIntoView` + `focus`。这是仓库既有「禁止在 focus 时程序滚动」规则的例外，已写进 `AGENTS.md`（只由点击触发）。模拟器下表现正常，真机要看。
- **第一次打字丢字**：见场景 3，没复现，原因未证实。
- **折扣口径**：全桌 / 待认领用按菜账本（折扣前）的合计，与 `result[].amount` 同口径；账单带折扣时，页面上「账单明细合计」（折后）可能和这里的「全桌」不一样，未实测。
- **「已呼叫结账」对遗留数据**：他人一张旧的、仍存在服务端的 `unlocked` 票也会显示「已呼叫结账」。新逻辑解锁时会删票，只有改版前的旧行会有，未造这样的数据。
- **分钱零头**：别人的认领变化会让我某道菜金额变 1 分（如冰水 €0.62 ↔ €0.61），与现有底栏行为一致，但菜卡上会看到数字变动。
- **葡语复数**：「1 prato(s)」是权宜写法；既有文案「1 adultos」本就不分单复数，没动。

# 本次改动业务场景测试报告 · 开台后套餐固定

分支 `fix/buffet-package-fixed-after-open`。

## 1. 本次修改

- 堂食开台确认后，套餐固定：楼面详情只展示当前套餐（不可再选），服务端 `intent=save` 若套餐 id 变化 → 409 `buffet_switch_locked`。
- 人数（含改到 0）不改套餐；0 人仍保留 0+0 人头行与套餐 id；菜价仍按原套餐。
- 点选套餐不再触发自动保存；只有 −/+ 人数才自动保存。
- 开台弹窗版本核对逻辑未改。

涉及：`buffet-order.ts`、`buffet-waiter-pipeline.ts`、`WaiterTableDetail*`、`CheckoutHeadcountAdjustModal`、`waiter-messages`、`docs/agent-sole-index.zh.md`。

## 2. 核心业务规则

1. 开台确认选中的套餐 → 本会话内不可更换（与人数无关）。
2. 改人数只改人头费份数；0 人套餐归属仍在，堂食菜价仍按该套餐。
3. 外卖不走堂食套餐开台。
4. 并台：套餐不同仍拒。

## 3. 详细测试场景

### 场景 1：开台后不能换套餐（正常）

- **前置状态**：白云空桌；店员已登录楼面。
- **操作过程**：开台选「Buffet livre」1 大 → 确认 → 进详情再企图点另一套餐。
- **预期结果**：详情只显示当前套餐（选项锁死）；无换套餐保存请求；合计跟人头仍为 Livre。
- **数据验证**：`current` buffet_id 仍为开台套餐。
- **异常恢复**：刷新详情仍锁在同一套餐。

### 场景 2：改人数到 0 仍保留套餐（正常）

- **前置状态**：场景 1 已开台桌。
- **操作过程**：大人 − 到 0（确认清人数对话框若出现）→ 保存。
- **预期结果**：人头费为 0；套餐仍显示原套餐；再点菜仍按原套餐价（非无套餐原价）。
- **数据验证**：仍有 active `buffet_base` 行，`adult_count/child_count=0`，`buffet_id` 不变。
- **异常恢复**：再 + 回 1 人，仍是原套餐锁价。

### 场景 3：API 强行换套餐被拒（权限/异常）

- **前置状态**：已开台桌。
- **操作过程**：`POST …/staff/waiter/buffet` `intent=save`，body 换成另一 `buffet_id`。
- **预期结果**：409 `buffet_switch_locked`。
- **数据验证**：订单套餐未变。

### 场景 4：开台弹窗点选不保存（回归）

- **前置状态**：空桌打开开台弹窗。
- **操作过程**：在未点确认前切换套餐选项。
- **预期结果**：无 `intent=save/open` POST；最多只有版本核对 GET。
- **数据验证**：桌仍空。

### 场景 5：同套餐改人数仍可用（回归）

- **前置状态**：已开台 1 大。
- **操作过程**：+ 到 2 大。
- **预期结果**：自动保存成功；人头费按开台锁价 ×2。

## 4. 实际测试结果

- 场景 3【已验证】A-05 POST 换 UAT 第二套餐 → 409 `buffet_switch_locked`
- 场景 2【已验证】同套餐人数→0：200；active 行仍 `buffet_id=Buffet livre`、0+0、price=0；菜品 Esporão 仍 €1.50
- 场景 5【已验证】人数→1：200；人头费恢复锁价 €19.95
- 场景 1【已验证】UI `:3002` 详情：仅「Buffet livre」一项且 radio disabled；无第二套餐选项；人数 −/+ 仍在
- 场景 4【未验证】开台弹窗点选不 POST（本次未再开空桌；代码路径点选已去掉 autosave）

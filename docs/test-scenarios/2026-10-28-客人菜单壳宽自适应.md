# 本次改动业务场景测试报告：客人菜单壳宽自适应

日期：2026-10-28  
分支：`fix/guest-menu-shell-width-adaptive`

## 1. 本次修改

- **内容**：客人点餐 / 账单相关页面壳宽改为「随视口变宽，上限约 1088px」；去掉原先「先锁 430px、到 1024 才放宽」的双段写法。
- **唯一写法**：`CUSTOMER_MENU_SHELL_WIDTH_CLASS = w-full max-w-[68rem]`（页面根、菜单底栏、账单底栏、购物车/已点 sheet、店招营业时间层、寿司过敏原层同宽）。
- **文件**：`customer-menu-chrome-layout.ts`、底栏/账单/店招/寿司条调用点、相关单测与设计/sole 文档；删除未再使用的 Tailwind `maxWidth.mobile`。
- **角色 / 页面**：顾客（及职员协助点餐同壳）— 菜单页、账单页；无结账规则 / DB 变更。

## 2. 核心业务规则

1. 【本次新增】壳宽只有一份：填满可用宽度，且不超过 `68rem`。
2. 【已实现】菜卡列数仍跟内容区宽度（容器查询），不另写平板专用列规则。
3. 【已实现】菜品详情：小于 `lg` 仍整屏；`lg+` 仍是独立 `max-w-lg` 对话框，不跟菜单壳。
4. 【已实现】不新增全屏按钮；不改职员 PWA。
5. 点餐 / 结账金额与状态机不变。

## 3. 详细测试场景

### 场景 1：手机竖屏菜单仍满宽单列

- **前置状态**：顾客打开 `/{slug}/menu?table_id=…`；视口约 390×844。
- **操作过程**：进入菜单，看店招与菜列表、底栏。
- **预期结果**：内容贴左右边（无大灰边）；菜卡 1 列；底栏与内容同宽。
- **数据验证**：不改订单数据。
- **异常恢复**：不适用。

### 场景 2：平板横屏菜单铺满（本需求主路径）

- **前置状态**：同上 URL；视口约 1024×768 或实机平板横屏。
- **操作过程**：打开菜单；必要时滚到菜列表。
- **预期结果**：左右不再出现「手机窄条 + 大灰边」；内容接近满宽（≤1088）；壳够宽时可 2 列菜卡；底栏同宽。
- **数据验证**：不改订单。
- **异常恢复**：刷新后宽度规则不变。

### 场景 3：电脑宽屏有上限居中

- **前置状态**：视口 ≥ 1400px。
- **操作过程**：打开菜单。
- **预期结果**：内容区最大约 1088px 居中，不无限拉满整屏。
- **数据验证**：无。
- **异常恢复**：无。

### 场景 4：账单页与点餐壳同宽

- **前置状态**：顾客进入账单页。
- **操作过程**：对照菜单页看内容区宽度。
- **预期结果**：账单页 / 底栏与菜单同一壳宽 token，无「菜单宽、账单又窄」。
- **数据验证**：分单数据不变。
- **异常恢复**：无。

### 场景 5：加菜 / 购物车 sheet 对齐壳宽（回归）

- **前置状态**：菜单已打开，购物车有菜或可加菜。
- **操作过程**：打开购物车或已点 sheet。
- **预期结果**：sheet 宽度跟菜单壳；可正常加减与关闭。
- **数据验证**：本地购物车行为与改前一致（本需求不改提交逻辑）。
- **异常恢复**：关闭 sheet 后可继续点菜。

### 场景 6：职员协助点餐同壳（回归）

- **前置状态**：职员从桌台进协助点餐（嵌入菜单）。
- **操作过程**：在宽视口看嵌入菜单。
- **预期结果**：与客人同一壳宽类；可浏览菜品。
- **数据验证**：无本需求写库。
- **异常恢复**：无。
